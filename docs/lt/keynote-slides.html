レビューを出す前に、1回だけ通す

Claude Code の /code-review を紹介する3〜5分のLT。この仕様書のとおりに Keynote で15枚作ると、撮影済みのキャプチャ12枚がすべて収まります。件数と実行時間はすべて実測値です。

スライド 15枚 キャプチャ 12枚 所要 4分56秒 medium 3件 / 54秒 聞き手 エンジニア中心

まだ埋まっていない数字が2つあります

high の 指摘件数と実行時間は、STEP7_4（メイン画面）を見てから確定します。仕様書内では 要確認 のタグを付けてあります。

キャプチャの「Agent "/code-review" finished · ○○s」の行に実行時間が、「○件の問題が見つかりました」に件数が出ています。そこを読んで置き換えてください。

話すこと

前提を先に言っておきます。モデルは Sonnet 5、effort は medium、Claude Code は v2.1.251 です。画面の上に実際の設定が出ています。

それからどの工程の話か。今日お見せするのは製造・単体実装のフェーズ、つまりコードを書き終えて人にレビューを出す直前です。今日出てくるバグは、結合試験まで行けば見つかるはずのものです。それをもっと手前で、自分ひとりで潰すという話をします。

このスライドを入れる理由

エンジニア相手だと「どの条件で？」「それ結合試験で見つかるでしょ」の2つが必ず出ます。両方をここで先に潰しておくと、以降の質問が消えて本題に集中できます。/model・/effort の画面は隠さず、環境を示す証拠として積極的に見せてください。

話すこと

このリポジトリの README には、会計上の決めごとが書いてあります。「粗利は売上マイナス原価」「利益分配は原価ではなく、粗利の中から払う」。

【ここで一拍おく】

コードではなく、README です。

実装はこれを守っておらず、分配を原価として引いていました。Claude はその README を読んだ上で、「これは README に書かれたルールへの違反だ」と指摘してきました。

文法チェックでも、よくあるバグパターンの検出でもないですよね。リポジトリの中の決めごとを読んで、それと突き合わせている。ここまでやるとは思っていませんでした。

この画像を出す理由

LTの結論そのもの。投影して、会場の一番うしろから文字が読めるか必ず確認してください。読めないなら、指摘部分を切り出して拡大するか、テキストで打ち直します。

話すこと

2つの違いです。時間は54秒に対して○秒、件数は3件に対して○件。

面白いのが探し方が変わるところです。medium のときは「差分が小さいので、8方向のエージェント群は立てずに手作業で確認した」と書いてありました。high では「8つの観点でエージェントを展開して候補を出し、重大なものは実際にビルドして動かして確かめた」と。

普段は引数なし、リリース前や大きめの差分だけ high、くらいの使い分けでいいと思います。

この内容の出どころ

推測ではなく、サブエージェントの画面にそう書いてあります（STEP6_1 と STEP7_3）。時間があれば該当箇所を切り出して添えると説得力が出ますが、なくても口頭で十分伝わります。

medium と high — 実測の比較

medium（引数なし）high
実行時間54秒要確認
指摘件数3件要確認
探し方 差分が小さいと判断し、8方向のエージェント群を立てずに手作業で検証（画面に明記） 8つの観点でエージェントを展開して候補を出し、重大なものは実際にビルド・実行して検証（画面に明記）
拾ったもの 符号の二重反転 ／ ゼロ除算 panic ／ Atoi のエラー握りつぶし 上記に加えて、share（分配）を原価に混ぜている点など
決めごとの参照 CLAUDE.md の「エラーは握りつぶさない」ルールを引用 README.md の会計ルール（粗利の定義・分配の扱い）を引用
向く場面 日常のレビュー前チェック。まずこれで十分 リリース前、大きめの差分、お金や権限を扱う箇所

質疑で聞かれたら

「毎回同じ結果が出る？」 — 出ません。同じ差分でも実行のたびに件数は変わります。実際、この差分を別の条件で流したときは medium で5件、high で8件でした。「当たり外れはあるが、出してくれるものは実際に動かして裏を取っている」という答え方が正確です。

5分枠のギリギリです

4分56秒は、緊張して早口になるぶんを差し引いてもかなり攻めた配分です。必ず一度、時計を見ながら通しで声に出して読んでください。超えるようなら下の順で削ります。

4分に収めたいとき — 削る順番

  1. 10（厳しさを上げる）を 11 に統合 → −8秒。11のスライドに /code-review high と併記すれば足ります
  2. 14 の使い方を --fix の1行だけに → −10秒
  3. 02 のつかみを1文に → −7秒
  4. 05 の説明を「130行のPR。buildもvetも通る」の一言で流す → −8秒
  5. 13 の比較を「時間と件数」だけにして、探し方の話を落とす → −12秒
  6. 08（コマンドを打つ）を落とす → −12秒。03 と内容が重なります

04・07・12 は削らない

04（前提）は質疑を封じるため、07（動いてしまうバグ）と12（決めごととの突き合わせ）はLTの中身そのものです。ほかを全部削ってでも、この3枚には時間を残してください。
