# デモ再現手順とキャプチャ撮影ポイント

手元でこのままなぞると、LTで見せる画面が再現できます。**撮影は7枚**。

## 準備

```
git clone https://github.com/shokawakita/claude-review-demo
cd claude-review-demo
git checkout feature/monthly-summary
go build ./...
```

ターミナルは投影を意識して設定しておきます。

- フォントサイズ **18pt 以上**
- **明るい背景テーマ**（暗い背景はプロジェクタで飛びます）
- ウィンドウ幅は狭め。横に長いと投影時に文字が小さくなります

---

## STEP 1 — 差分を見せる

```
git diff --stat main..HEAD
```

```
 cmd/kaihi/main.go          | 13 +++++++--
 internal/ledger/ledger.go  | 51 ++++++++++++++++++++++++++++++++++
 internal/report/summary.go | 68 ++++++++++++++++++++++++++++++++++++++++++++++
 3 files changed, 130 insertions(+), 2 deletions(-)
```

130行の、ごく普通のサイズのPRです。

> 📸 **キャプチャ①**：この `--stat` の出力。

## STEP 2 — ビルドもvetも通ることを見せる

```
go build ./... && go vet ./... && echo "OK"
```

**両方とも無警告で通ります。** ここが効きます。
静的解析では見つからない、という前提を先に潰しておきます。

> 📸 **キャプチャ②**：`OK` まで出た画面。

## STEP 3 — 実装を見せる

```
sed -n '25,50p' internal/report/summary.go
```

集計の中心部分です。全部は映さず、`Build()` のループのあたりだけ。

> 📸 **キャプチャ③**：`Build()` の中身。
> エディタで開いてシンタックスハイライトを効かせたほうが読みやすいです。

## STEP 4 — 動かす。エラーは出ない ★重要

```
go run ./cmd/kaihi 2026-01
```

```
=== 2026-01 の収支 ===
売上          :    20000 円
支出          :   -16800 円
粗利          :    36800 円
イベント数    :        1 件
1件あたり粗利 :    36800 円
--- 費目別内訳 ---
参加費                     20000 円
会場費                    -12000 円
分配（企画主担当）               -4800 円
```

台帳の中身は「売上 20,000／会場費 12,000／分配 4,800」。
**正しい粗利は 8,000 円、手元に残るのは 3,200 円。表示は 36,800 円。**
支出がマイナスで記録されているのに引き算しているため、符号が反転しています。

**エラーは出ません。終了コードも 0 です。**

> 📸 **キャプチャ④**：この出力。
> Keynote 側で「36800」に赤枠を付けます。

### 余裕があれば見せる（口頭で触れるだけでも可）

```
go run ./cmd/kaihi 2026-03    # 金額 "1,500" が 0 になり、赤字が黒字に見える
go run ./cmd/kaihi 2026-12    # panic: integer divide by zero
go run ./cmd/kaihi 2026       # 月のつもりが1年分の合計を出す。終了コードは 0
```

費目の並び順が実行のたびに変わることも見せられます（map の反復順）。

```
for i in 1 2 3; do go run ./cmd/kaihi 2026-01 | tail -3; echo ---; done
```

## STEP 5 — `/code-review` を打つ

```
claude
```

```
/code-review
```

引数なしで、いまのブランチの差分を自動で見つけます。

> 📸 **キャプチャ⑤**：`/` を打ってコマンド候補が出ている画面。
> 候補リストごと撮ると「他にもコマンドがある」が伝わります。

## STEP 6 — medium の結果（5件）

> 📸 **キャプチャ⑥**：指摘5件が並んでいる画面。
> 全部読めなくてよいです。件数と、ファイル名:行番号 が付いていることが伝わればOK。

## STEP 7 — high に上げる（8件）★山場

```
/code-review high
```

> 📸 **キャプチャ⑦**：8件出た画面。
> **2件目（`share` を原価として扱っている、という README ルール違反の指摘）が
> 読める大きさで映っていること。** この1枚だけは文字サイズを優先してください。
> 最後の総括の一文まで入るとなお良いです。

---

## 撮影のコツ

- `Shift + Command + 4` → `Space` でウィンドウ単位の影付きキャプチャ
- 影が邪魔なら `Space` の後に `Option` を押しながらクリック
- 貼る前に、他の作業タブ・APIキー・個人情報の映り込みを必ず確認

## 発表後に聞かれそうなこと

**Q. 実行にどれくらいかかる？**
このサイズ（130行）で1〜2分。high にすると少し伸びます。

**Q. medium と high の違いは？**
low から max まであります。低いほど「確実なものだけ」、高いほど広く拾い、
確度の低いものも混ざります。今回は high で3件増えました。

**Q. 嘘の指摘（ハルシネーション）は出ない？**
出ないとは言えません。今回の8件は全部、実際にビルドして動かした裏取り付きで
返ってきました（出力にもその旨が書かれています）が、鵜呑みにせず差分は自分で見ます。
