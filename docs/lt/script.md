# LT台本：「レビューを出す前に、1回だけ通す」

- **持ち時間**：4分（3〜5分枠の真ん中。巻いても伸びても収まる）
- **スライド**：10枚
- **聞き手**：エンジニア中心。専門用語はそのまま使う
- **読み上げ量**：約1,350字。ゆっくり話して4分ちょうど

`【 】` は動作の指示なので読み上げません。

---

## スライド1 — タイトル（15秒）

> レビューを出す前に、1回だけ通す
>
> Claude Code `/code-review`

**話すこと**

> Claude Code の機能をひとつだけ紹介します。コードレビューです。
> 4分後には、今日から打てるコマンドを1つ持って帰れます。

---

## スライド2 — つかみ（25秒）

> レビュー依頼、少し身構えませんか

**話すこと**

> レビューを出すとき、少し身構えませんか。
> 初歩的なミスでレビュアーの時間を取るのが申し訳ない、とか。
> あと単純に、レビュー待ちで手が止まるのがもったいない。
> 人に出す前に自分で一回潰せたらいいなと思って、実際に試してみた話をします。

---

## スライド3 — 結論（20秒）

> `/code-review`
>
> 引数なし。いまの差分を自動で拾う

**話すこと**

> 結論はこれだけです。Claude Code を起動して `/code-review`。
> 引数もファイル名も要りません。**いまのブランチの差分を自動で見つけて**レビューします。
> 実際にやってみたので、画面を見てください。

---

## スライド4 — 題材（25秒）

> 【📸 ①】`git diff --stat` → 130行 / 3ファイル
> 【📸 ②】`go build && go vet` → 無警告

**話すこと**

> 題材は Go の小さな CLI です。CSVの台帳を読んで、月ごとの収支を集計するだけ。
> 差分は3ファイル130行。よくあるサイズのPRだと思います。
> **build も vet も無警告で通ります。** 静的解析では何も出ません。

---

## スライド5 — 動かす（35秒）★空気が変わる

> 【📸 ④】実行結果
>
> 粗利：36,800円 ←赤枠
> 正しくは 8,000円

**話すこと**

> 動かします。エラーは出ません。終了コードも 0 です。
> 【間をとる】
> でも間違っています。正しい粗利は 8,000円。表示は 36,800円。4倍以上ずれています。
> 支出をマイナスで持っているのに、さらに引き算していたので符号が反転していました。
> こういうのが一番こわいと思っていて、**落ちないので誰も気づかない。**
> テストがあっても、この期待値で書いてしまえば通ってしまいます。

---

## スライド6 — 打つ（15秒）

> 【📸 ⑤】`/code-review` 入力画面

**話すこと**

> ここでコマンドを打ちます。スラッシュを打つと候補が出るので選ぶだけ。
> このサイズなら1〜2分で返ってきます。

---

## スライド7 — medium：5件（30秒）

> 【📸 ⑥】指摘5件
>
> 全件「実際にビルドして動かした」裏取り付き

**話すこと**

> 5件出ました。細かく読まなくて大丈夫です。
> さっきの符号バグはもちろん入っています。ファイル名と行番号つきで、
> 「実際に動かすとこう出る、正しくはこう」まで書いてあります。
> **推測ではなく、実際にビルドして実行した上での指摘**だと明記されています。
> ここまでは、正直まあそうだろうなと思っていました。
> 驚いたのはこの次です。

---

## スライド8 — high：8件（50秒）★山場。一番時間をかける

> 【📸 ⑦】`/code-review high` → 8件
>
> 「README の集計ルールに違反している」

**話すこと**

> 厳しさを上げられます。low から max まであって、high にすると 8件に増えました。
> 増えた中にこれがありました。
> 【間をとる】
> このリポジトリの README には、会計上の決めごとが書いてあります。
> 「粗利は売上マイナス原価」「利益分配は原価ではなく、粗利の中から払う」。
> **コードではなく、README です。**
> 実装はこれを守っておらず、分配を原価として引いていました。
> Claude はその README を読んだ上で、
> 「この2つは README に書かれたルールへの違反だ」と指摘してきました。
> 文法チェックでも、よくあるバグパターンの検出でもないですよね。
> **リポジトリの中の決めごとを読んで、それと突き合わせている。**
> ここまでやるとは思っていませんでした。

---

## スライド9 — 使い方（30秒）

> `/code-review` … 引数なしでOK
> `/code-review high` … 厳しさ low〜max
> `/code-review --fix` … その場で直す
> `/code-review --comment` … PRに行コメントを投稿

**話すこと**

> 使い方です。基本は引数なしでいいです。
> 物足りなければ high や max。今回は medium から high で3件増えました。
> `--fix` を付けると指摘するだけでなくその場で直します。
> `--comment` を付けると GitHub のPRに行ごとのコメントとして投稿してくれます。

---

> まとめます。人にレビューを出す前に1回だけ通してみてください。

## 3分に縮めるなら

1. **スライド6**（コマンド入力画面）を落とす → −15秒。スライド3と重複
2. **スライド9**を `--fix` の1行だけにする → −15秒
3. **スライド4**を「130行のPR。buildもvetも通る」の一言で流す → −15秒
4. **スライド2**のつかみを1文に → −10秒

**スライド5と8は削らないでください。** この2枚が中身です。

## 5分に伸ばすなら

スライド8のあとに1枚足して、他に何が出たかを口頭で3件:

- 該当データのない月で `integer divide by zero` の panic
- 金額 `"1,500"` が `strconv.Atoi` のエラー握り潰しで 0 になり、赤字が黒字に見える
- 費目別内訳が map の反復順で、実行のたびに並び順が変わる（golden test が flaky になる）

3つ目はライブで `for i in 1 2 3` を回して見せると効きます。
